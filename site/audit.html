L’audit RGAA complet

Dans l’agent, une phrase suffit : « audite ce site selon le RGAA ». La skill ultra11y suit alors le même parcours sur Claude Code, Codex et OpenCode, décrit dans references/full-audit.md. Chaque étape est une commande du moteur ; l’agent tient le rôle de l’auditeur.

Le déroulé

  1. Le périmètre. L’agent confirme le référentiel, la langue et l’échantillon de pages (accueil, contact, mentions légales, formulaires…), déclaré dans .ultra11yrc.json. Sans échantillon, il parcourt le site.

  2. Le code et les pages rendues. Le moteur statique lit le code source, puis chaque page est ouverte dans un vrai navigateur : axe-core, sondes de focus, zoom, espacement et survol. Sans cette capture, les critères de rendu restent « à évaluer » ; un rapport sans elle est signalé comme partiel.

  3. L’arbitrage. Pour chaque critère non tranché, l’agent reçoit une fiche : les preuves collectées et le texte officiel du critère, avec ses tests et son glossaire. Il conclut, preuve à l’appui. Sur un gros site, il répartit les fiches entre des sous-agents.

  4. La contre-vérification. Chaque verdict écrit est remis en cause, les « conforme » et « non applicable » compris. Ce qui ne tient pas est retiré ou repart « à évaluer ».

  5. Le registre et les livrables. Les verdicts acceptés sont consignés dans un registre, rejoué et revérifié au prochain audit. L’agent publie le rapport, la grille et les dossiers de pages.

  6. Le contrôle final. check valide chaque livrable et échoue tant qu’un critère reste « à évaluer » sans raison déclarée. Un contrôle en échec fait partie du résultat : il n’est jamais présenté comme un rapport complet.

L’IA juge, puis se fait contredire

Exemple. L’IA met le critère 1.1 en conforme parce que l’image a alt="logo". La contre-vérification réfute : cela prouve qu’une alternative existe, pas qu’elle décrit l’image. Le critère repart « à évaluer ». Il ne passe pas en non conforme : réfuter une conformité ne prouve rien contre le critère.

Les quatre statuts d’un critère

C : conforme
Le critère est respecté, et le verdict cite les éléments vérifiés.
NC : non conforme
Au moins un élément réel échoue à un test. La non-conformité pointe vers la page, le fichier et la ligne.
NA : non applicable
Le critère ne concerne pas la page (pas de vidéo, pas de tableau…). Le NA est justifié, et contre-vérifié comme un « conforme » : il compte comme un succès dans le taux.
À évaluer
Personne n’a encore tranché. Ni échec ni réussite : un travail restant, affiché comme tel. Le moteur ne conclut jamais « conforme » sur un silence, sauf pour 8.3 et 8.5 (langue et titre de la page).

Les livrables

  • Le rapport RGAA daté, en Markdown et en HTML imprimable : résumé, synthèse par thématique, non-conformités par priorité, critères à évaluer, puis une annexe technique avec les occurrences.
  • La grille page par page : une ligne par critère, une colonne par page, le taux de conformité de chaque page (conformes ÷ décidés) et le taux moyen de l’échantillon.
  • Un dossier par page : sa capture d’écran, son taux, chacun des 106 critères avec son statut, et chaque non-conformité illustrée.
  • Sur demande, un backlog et des tickets GitHub, GitLab ou Jira : un ticket par critère, par page ou par fichier. Relancer ne crée pas de doublon.

Chaque non-conformité y est décrite par le même bloc d’auditeur : thématique, critère et intitulé officiel, test, constat, état attendu, méthode de vérification, occurrences. Le rapport, les dossiers et les tickets ne peuvent donc pas se contredire.

Capturer les pages depuis vos tests

Le navigateur de l’audit ouvre les pages sans l’état que vos tests construisent : pas de session connectée, pas de formulaire rempli, pas de fenêtre modale ouverte. La bibliothèque audite au contraire la page telle que votre test l’a laissée, et l’enregistre dans .ultra11y/pages/<id>/ : l’audit complet la reprend ensuite, hors ligne. Elle s’installe avec npm i -D ultra11y.

import { test } from "ultra11y/playwright";

test("tableau de bord", async ({ page, ultra11y }) => {
  await page.goto("/tableau-de-bord");
  await ultra11y({ as: "tableau-de-bord" });   // ou checkA11y(page, { as: "tableau-de-bord" })
});

Avec Cypress, deux branchements : ultra11y(on) dans setupNodeEvents (importé depuis ultra11y/cypress/plugin) et import "ultra11y/cypress" dans le fichier de support. Puis, dans un test :

cy.visit("/");
cy.ultra11y({ as: "accueil" });

sweepSample() parcourt d’un coup l’échantillon déclaré dans .ultra11yrc.json. failOn: false enregistre sans faire échouer le test : pratique pour démarrer sur un projet qui a déjà une dette. Toutes les options : references/e2e.md.

En CI : le bot rgaa-audit d’iterion

ultra11y ne fournit pas d’intégration CI à lui seul. En CI, l’audit passe par le bot rgaa-audit d’iterion : il installe le moteur à une version épinglée, rend les pages de l’échantillon, fait arbitrer les critères de jugement par des agents en lecture seule, soumet chaque verdict à un second lecteur, contrôle le résultat avec check, puis ouvre un ticket par critère non conforme.

Le moteur seul, sans agent, ne fait pas un audit : les critères de jugement resteraient « à évaluer ». La mise en place est décrite dans le README du bot ; le contrat entre les deux est dans references/ci.md.

Avant chaque commit : la revue du changement

Pendant le développement, la skill review-a11y relit le diff avant chaque commit, push ou pull request, grâce au hook installé avec l’extension (voir Installer). Après un audit, la skill ultra11y lui confie aussi le diff corrigé, dans un sous-agent qui part d’un contexte vierge.
