RGAA 4.1.2 · le référentiel d’accessibilité de l’État

ultra11y : l’audit d’accessibilité RGAA qui dit ce qu’il ne sait pas vérifier

ultra11y audite un site selon le RGAA 4.1.2. C’est une skill pour votre agent de code (Claude Code, Codex, OpenCode) : vous demandez un audit, l’agent le mène de bout en bout et vous remet un rapport de conformité daté. Il ne déclare jamais conforme ce qu’il n’a pas vérifié.

  • 102vérifications automatiques sur le code source, sans navigateur
  • 0fausse alerte non expliquée sur 401 exemples corrects du corpus officiel du W3C

Ce que vous obtenez

  • Le rapport RGAA daté, en Markdown et en HTML imprimable : résumé, synthèse par thématique, non-conformités par priorité, critères restant à évaluer.
  • La grille des 106 critères, page par page, avec le taux de conformité de chaque page et le taux moyen de l’échantillon : les chiffres qu’attend une déclaration d’accessibilité.
  • Un dossier par page, avec sa capture d’écran et chaque non-conformité illustrée.
  • Sur demande, un backlog et des tickets GitHub, GitLab ou Jira.

Comment ça marche

Chacun son travail : la machine décide ce qu’elle sait prouver, l’IA juge le reste sous contrôle, et les garde-fous renvoient tout verdict sans preuve.

Un moteur déterministe

Même code, même résultat. Le moteur lit le code source et applique 102 vérifications : image sans alt, champ sans étiquette, page sans langue, tableau sans en-têtes… Hors ligne, sans clé ni compte.

Un passage dans le navigateur

Chaque page de l’échantillon est ouverte dans un vrai navigateur, avec axe-core et des sondes : contraste réel, focus visible, zoom à 200 %, affichage sur petit écran.

Un agent IA qui juge, sous contrôle

La plupart des tests RGAA demandent un jugement : cette alternative décrit-elle l’image ? ce lien est-il explicite ? L’agent tranche à partir des preuves collectées, et chaque verdict cite ce qu’il a lu.

Des garde-fous

Chaque verdict de l’IA est remis en cause avant d’entrer dans le taux. check et verify refusent un critère inventé, une non-conformité sans élément réel, un « conforme » sur des preuves incomplètes.

Trois façons de s’en servir

  1. Demander un audit à l’agent : « audite ce site selon le RGAA ». Le déroulé.

  2. Capturer les pages depuis vos tests Playwright ou Cypress, dans l’état où le test les a laissées (session connectée, formulaire rempli). La bibliothèque.

  3. Auditer en CI avec le bot rgaa-audit d’iterion. Les détails.

Installé comme extension, ultra11y relit aussi chaque changement avant un commit, un push ou une pull request.

Ce que ce n’est pas

  • Pas une certification. Un rapport ultra11y prépare un audit RGAA. Avant une déclaration d’accessibilité officielle, une personne compétente relit les verdicts de jugement.
  • Pas un « score ». Le taux porte sur les critères décidés. Ce qui n’a pas été vérifié reste « à évaluer », jamais « conforme » par défaut.
  • Pas infaillible côté IA. Les garde-fous vérifient que l’IA cite ses preuves, pas qu’elle juge juste. Voir Fiabilité.
  • Pas Lighthouse. Lighthouse exécute une partie des règles d’axe-core. ultra11y utilise axe-core directement et ajoute ses propres règles.

Le RGAA reprend les WCAG 2.2 niveau AA, qui servent de socle au moteur.
